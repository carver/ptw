# Speech-to-text backends for ptw

Researched 2026-08-28. Target: CPU-only Intel Alder Lake (16 threads, AVX2 + AVX-VNNI, no AVX-512), 15 GB RAM, Ubuntu. Requirements: hold a key, speak, text streams out while speaking, English first, fully offline, feels like Handy, single Rust binary (linking C/C++ is fine, a Python runtime is not), and a way to bias recognition toward user-supplied names and jargon.

Every claim below links to the primary source I read. Numbers from third-party blogs are not used. Where I could not verify something I say so in the last section.

## Short version

Ranked for this project:

1. Nemotron Speech Streaming EN 0.6B (NVIDIA, cache-aware transducer) through either sherpa-onnx (official `sherpa-onnx` Rust crate) or transcribe.cpp (`transcribe-cpp` crate, what Handy ships today). Native streaming, 80 ms to 1.12 s lookahead, punctuation and casing, roughly 7 to 9x realtime on a mediocre laptop CPU, ~700 MB at int8/Q8_0. Hotwords: in sherpa-onnx behind an open PR (#3895, Aug 24 2026); in transcribe.cpp none, Handy fixes words after the fact.
2. Moonshine v2 streaming (medium 245M / small 123M), via its C API (`libmoonshine.so` + bundled onnxruntime, prebuilt for Linux x86_64) or the transcribe.cpp GGUF port. Native streaming, MIT models, the only candidate with shipped contextual biasing (`moonshine_transcriber_set_keyterms`). Measured end-of-phrase latency 258 ms for medium on an Apple M3. Accuracy a notch below Nemotron (6.65% vs ~6.9% Open ASR average, but Nemotron's LibriSpeech numbers are much better).
3. whisper.cpp via whisper-rs (or whisper-cpp-plus, which ports the `stream` example). Fallback only. Whisper is not a streaming model; "streaming" is re-decoding a sliding window every ~500 ms, and only base/small are realtime on CPU. Custom vocabulary is an `initial_prompt` text hint.

Not recommended: Kyutai STT (no CPU numbers anywhere, 1B to 2.6B params, GPU-oriented Rust server), Voxtral Realtime (4B, ~8 GB weights, decoder step 335 ms on an M3 Max CPU), WhisperLive and SimulStreaming (Python servers; SimulStreaming's README says CPU is too slow for realtime), Vosk (fine engine but 2019-era accuracy and the Rust crate is stale), sherpa-onnx Zipformer English streaming models (2023, LibriSpeech-only training, UPPERCASE no punctuation).

## What Handy does today

Handy is the reference feel, so I checked what it actually runs.

- Rust + Tauri, MIT. v0.9.6 released 2026-08-24, pushed to daily. ([repo](https://github.com/cjpais/Handy), GitHub API)
- Engines in `src-tauri/Cargo.toml`: `transcribe-rs` 0.3.8 with the `onnx` feature (Parakeet, Moonshine, SenseVoice, Canary and others through the `ort` crate) and `transcribe-cpp` 0.2.0 (GGUF models on ggml, with `dynamic-backends` + Vulkan on Linux). VAD is `vad-rs` (Silero). ([Cargo.toml](https://raw.githubusercontent.com/cjpais/Handy/main/src-tauri/Cargo.toml))
- Streaming arrived in 0.9.0 (2026-07-01) with the transcribe.cpp integration. Only transcribe.cpp models stream; the ONNX engines fall back to batch-after-release ([issue #1830 comment](https://github.com/cjpais/Handy/issues/1830)). The live path shows a preview while you talk and commits on release.
- Which models stream well on CPU, from Handy's own users: Nemotron "works fine, even at the lowest latency setting, since they use cache aware streaming and therefore do not have to recompute left context every time"; Parakeet Unified lags on CPU at the two lowest latency settings ([PR #1666 comment](https://github.com/cjpais/Handy/pull/1666)). A separate report measured Parakeet Unified Q8_0 streaming at 0.18 to 0.30x realtime on a 16-core desktop CPU because the encoder re-runs over accumulated audio ([issue #1754](https://github.com/cjpais/Handy/issues/1754)). Parakeet TDT v3 GGUF is offline-only by architecture ([issue #1830](https://github.com/cjpais/Handy/issues/1830)).
- Custom vocabulary: Handy has a "Custom Words" post-processing step, not decoder biasing. It fuzzy-matches (Levenshtein) transcript words against the user's list, and since PR #711 (merged 2026-02-05) matches 1 to 3 word n-grams so "Chat G P T" becomes "ChatGPT". PR #1406 (merged 2026-08-17) allowed spaces in custom words. ([PR #711](https://github.com/cjpais/Handy/pull/711), [PR #1406](https://github.com/cjpais/Handy/pull/1406))
- Handy's README states Parakeet V3 runs about 5x realtime on mid-range CPUs (Skylake or newer) and Whisper wants a GPU. transcribe-rs README: Parakeet int8 "Zen 3 ~20x real-time; Skylake ~5x". ([transcribe-rs README](https://raw.githubusercontent.com/cjpais/transcribe-rs/main/README.md))

Takeaway: Handy's authors already went through this search and landed on NVIDIA's cache-aware streaming transducers plus Moonshine streaming, on a ggml runtime with a Rust crate. That is a strong prior.

## Candidates

### 1. whisper.cpp via whisper-rs

- License MIT. v1.9.3 released 2026-08-20, commits daily. ([releases](https://github.com/ggml-org/whisper.cpp/releases), GitHub API)
- Model memory (README): tiny 273 MB, base 388 MB, small 852 MB, medium 2.1 GB, large 3.9 GB. Quantization q4_0/q5_0/q8_0 supported. ([README](https://github.com/ggml-org/whisper.cpp))
- Streaming approach: there is none in the model. The `stream` example "samples the audio every half a second and runs the transcription continuously" over a `--length` window (default 5 s), re-decoding the window each `--step`; `--step 0` switches to VAD-gated chunks. Text can change under you until a window is finalized. ([stream README](https://github.com/ggml-org/whisper.cpp/blob/master/examples/stream/README.md))
- Speed on CPU: the README example for realtime is `ggml-base.en.bin` with 8 threads. The bench thread's Ryzen 9 5950X (AVX2, 8 threads) encode times for one 30 s window: tiny 197 ms, base 421 ms, small 1393 ms, medium 4404 ms, large 8118 ms ([issue #89](https://github.com/ggml-org/whisper.cpp/issues/89)). transcribe.cpp's Whisper doc says the same thing: "tiny and base run in near-realtime on CPU; large typically wants Metal or a recent CUDA GPU" ([whisper.md](https://raw.githubusercontent.com/handy-computer/transcribe.cpp/main/docs/models/whisper.md)). Alder Lake will be slower than a 5950X. Expect base.en to be the comfortable realtime ceiling with the 500 ms step, small.en marginal, turbo no.
- Quant note: on a no-AVX CPU q5_0/q5_1 were 3 to 5.5x slower than q4_0 ([discussion #3752](https://github.com/ggml-org/whisper.cpp/discussions/3752)). That machine lacked AVX2 so don't over-read it, but prefer q8_0 or q4_0 and measure.
- WER: base.en/small.en are well behind the transducers. Open ASR averages from the Moonshine v2 paper's plot put whisper-large-v3 near 7.4% and turbo near 7.8%; small/base are 10%+ ([paper Fig 4](https://arxiv.org/pdf/2602.12241)).
- VAD: built-in Silero VAD (`whisper_vad_*` API, `vad_model_path`, `whisper_vad_detect_speech_no_reset` for streaming). ([whisper.h](https://raw.githubusercontent.com/ggml-org/whisper.cpp/master/include/whisper.h))
- Custom vocabulary: `initial_prompt` text (max ~224 tokens) prepended to the decoder context, plus `prompt_tokens`, `no_context`, `single_segment` ("useful for streaming"). This is a hint, not biasing; it helps spelling of names sometimes and can cause hallucinated prompt text on silence.
- Rust: `whisper-rs` 0.16.0 (2026-03-12, 1.04M downloads, Unlicense). The GitHub repo was archived 2025-07-30 and moved to [Codeberg](https://codeberg.org/tazz4843/whisper-rs), last commit March 2026. Builds whisper.cpp with cmake through `build.rs`; Linux "should just work". `FullParams` has `set_initial_prompt`, `set_tokens`, `set_no_context`, `set_single_segment`, `set_audio_ctx`, `set_vad_model_path`, `enable_vad`, and `set_new_segment_callback`. ([docs.rs](https://docs.rs/whisper-rs/latest/whisper_rs/struct.FullParams.html))
- `whisper-cpp-plus` 0.1.5 (2026-06-13, MIT, 3.2k downloads) is a separate binding that ports `stream.cpp` (`WhisperStream`, `WhisperStreamPcm`, `AsyncWhisperStream`) and a Silero VAD processor. Young, one author. ([docs.rs](https://docs.rs/whisper-cpp-plus/latest/whisper_cpp_plus/)) `whisper-stream-rs` 0.3.0 pins whisper-rs 0.14 and has 676 downloads; skip.

Verdict: the safest build, the worst fit. Chunked re-decode means text flickers, latency is step + decode time (~1 s with base.en), and accuracy is the lowest of the shortlist.

### 2. Kyutai STT (delayed streams modeling)

- Models: `kyutai/stt-1b-en_fr` (~1B, EN/FR, 0.5 s delay, semantic VAD) and `kyutai/stt-2.6b-en` (2.6B, EN, 2.5 s delay). Weights CC-BY-4.0, Rust code Apache-2.0. Natively streaming (Mimi codec at 12.5 Hz, decoder-only transformer). 2.6B reports mean WER 6.4, RTFx 88 on GPU. ([repo](https://github.com/kyutai-labs/delayed-streams-modeling), [1b card](https://huggingface.co/kyutai/stt-1b-en_fr), [2.6b card](https://huggingface.co/kyutai/stt-2.6b-en))
- Rust: `moshi` crate 0.6.4 (2025-10-01) on candle, plus `moshi-server`. Every documented command uses `--features cuda` or `metal`; the README's performance claims are L40S and H100 batch throughput. No CPU statement anywhere in the README, model cards, or the issue tracker. ([README](https://raw.githubusercontent.com/kyutai-labs/delayed-streams-modeling/main/README.md))
- RAM: 1B params in bf16 is ~2 GB of weights, f32 ~4 GB; the 2.6B is ~6 GB bf16. Fits in 15 GB.
- Custom vocabulary: an experimental text/audio prompt example "for nudging the model for a specific spelling of a word", flagged as "very sensitive to the prompt provided". ([README](https://raw.githubusercontent.com/kyutai-labs/delayed-streams-modeling/main/README.md))
- Activity: DSM repo last push 2026-01-26; moshi repo 2026-05-16.

Verdict: architecturally the nicest streaming design here, but a 1B autoregressive step every 80 ms on CPU through candle is unproven and the project doesn't target CPU. Would need a prototype to even know if it's realtime. Not a safe bet.

### 3. sherpa-onnx (official Rust crate)

- Apache-2.0. v1.13.6 released 2026-08-18, pushed to daily, 14.5k stars. ([releases](https://github.com/k2-fsa/sherpa-onnx/releases), GitHub API)
- Rust: the official `sherpa-onnx` crate 1.13.6 (2026-08-24, 293k downloads) wraps the C API. It links statically by default and, if `SHERPA_ONNX_LIB_DIR` is unset, its build script downloads a matching prebuilt archive from GitHub releases (Linux x86_64/aarch64, macOS, Windows), so no cmake and no onnxruntime hunt. `OnlineRecognizer` (streaming), `OfflineRecognizer`, `VoiceActivityDetector` are exposed. Docs coverage is ~25%. ([docs.rs](https://docs.rs/sherpa-onnx), [crates.io](https://crates.io/crates/sherpa-onnx)) The older community `sherpa-rs` crate was archived 2026-06-06 and points at the official one. ([sherpa-rs](https://github.com/thewh1teagle/sherpa-rs))
- Hotwords: `OnlineRecognizerConfig` has `hotwords_file`, `hotwords_buf`, `hotwords_score`, `decoding_method` ("greedy_search | modified_beam_search"), `blank_penalty`, endpoint rules. `OnlineModelConfig` has `model_type`, `modeling_unit`, `bpe_vocab`, `num_threads`, `provider`. ([OnlineRecognizerConfig](https://docs.rs/sherpa-onnx/latest/sherpa_onnx/struct.OnlineRecognizerConfig.html), [OnlineModelConfig](https://docs.rs/sherpa-onnx/latest/sherpa_onnx/struct.OnlineModelConfig.html)) Hotwords work only for transducer models with `modified_beam_search`; the file is one phrase per line, English in UPPERCASE for bpe models, optional `:score` suffix, matched with an Aho-Corasick context graph. ([hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html))
- Streaming English models available:
  - Nemotron Speech Streaming EN 0.6B, exported 2026-04-25, int8 only, one package per chunk size (80/160/560/1120 ms). 560 ms package: encoder 623 MB, decoder 6.9 MB, joiner 1.7 MB. Docs show RTF 0.16 on a 6.6 s file (hardware unstated). Greedy search only. ([nemotron page](https://k2-fsa.github.io/sherpa/onnx/nemo/nemotron-streaming.html)) A user in issue #3572 measured Nemotron streaming at WER 12.6% / RTF 0.036 vs Whisper Turbo offline 11.6% / RTF 0.140 on a 62 s clip (hardware unstated). ([#3572](https://github.com/k2-fsa/sherpa-onnx/issues/3572))
  - Nemotron 3.5 ASR Streaming 0.6B (40 locales), exported 2026-06-11, same shape.
  - Zipformer streaming EN (2023-02/06 exports): 68 to 180 MB int8 encoders, RTF 0.06 to 0.10 on CPU, but trained on LibriSpeech (+GigaSpeech for one), output is UPPERCASE without punctuation. ([zipformer page](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html)) No new English streaming Zipformer since 2023.
  - Parakeet TDT 0.6b v2/v3 and Parakeet Unified: offline only in sherpa-onnx (the "simulate streaming microphone" examples are VAD + batch). ([nemo transducer page](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-transducer/nemo-transducer-models.html))
  - Moonshine v2 is also runnable (`run-moonshine-v2.sh` in `rust-api-examples`), but I did not verify it uses the streaming path.
- The catch for this project: hotwords + Nemotron. `OnlineRecognizerTransducerNeMoImpl` rejects `modified_beam_search`, so the best English streaming model has no biasing path today. PR #3895 (opened 2026-08-25, open as of this writing) ports the offline NeMo beam search to streaming and reports hotwords fixing "Melchizedek", "Zerubbabel", "Epaphroditus" with beam=4 at ~1.1x greedy wall time and RTF ~0.11 on a 2-thread macOS CPU. Once merged it lands in the Rust crate automatically because the crate tracks upstream releases. ([#3895](https://github.com/k2-fsa/sherpa-onnx/pull/3895), [#3572](https://github.com/k2-fsa/sherpa-onnx/issues/3572))
- Threads: onnxruntime int8 kernels use VNNI where present; Alder Lake's AVX-VNNI is the 256-bit variant and ORT's MLAS has AVX2/AVX-VNNI int8 paths. I did not benchmark this.

Verdict: best engineering path if the hotwords PR merges. Zero-build-pain Rust crate, endpointing built in, model swap is a config change.

### 4. NVIDIA Parakeet / Nemotron on CPU, and parakeet-rs / parakeet.cpp / transcribe.cpp

Model facts:

- `parakeet-tdt-0.6b-v2` (EN, CC-BY-4.0, 2025-05-01): Open ASR avg WER 6.05%, LibriSpeech clean 1.69 / other 3.19. Offline model, full attention, 24 min max. ([card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2))
- `parakeet-tdt-0.6b-v3` (25 languages, CC-BY-4.0, 2025-08-14): avg 6.34%, clean 1.93 / other 3.59. Offline. ([card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3))
- `nemotron-speech-streaming-en-0.6b` (EN, NVIDIA Open Model License, 2026-01-05, updated 2026-03-12): cache-aware FastConformer-RNNT, chunk options 80/160/560/1120 ms, avg WER 6.93% at 1.12 s and 8.43% at 80 ms, LibriSpeech clean 2.32 / other 4.84 at 1.12 s. Punctuation and casing. GPU-only in the card. ([card](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b))
- `nemotron-3.5-asr-streaming-0.6b` (40 locales, OpenMDW-1.1, 2026-06-04): same architecture plus language prompt; English FLEURS 7.91% at 1.12 s. ([card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b))
- `parakeet-unified-en-0.6b` (NVIDIA Open Model License, 2026-04-07): offline 5.91%, streaming 6.52% at 560 ms, 8.44% at 160 ms. But it is buffered streaming with left-context recompute, not cache-aware, which is why it crawls on CPU (see Handy above). ([card](https://huggingface.co/nvidia/parakeet-unified-en-0.6b))
- `parakeet_realtime_eou_120m-v1` (NVIDIA Open Model License): 120M cache-aware RNNT, 160 ms chunks, avg WER 9.30%, emits an `<EOU>` token. ([card](https://huggingface.co/nvidia/parakeet_realtime_eou_120m-v1))
- NVIDIA Open Model License: commercial use and redistribution allowed with an attribution notice. ([license](https://www.nvidia.com/en-us/agreements/enterprise-software/nvidia-open-model-license/))
- Custom vocabulary from NVIDIA's side is NeMo-only (word boosting, n-gram LM shallow fusion, fine-tuning). ([HF discussion](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b/discussions/11))

Runtimes:

- `parakeet-rs` 0.3.7 (2026-07-28, MIT OR Apache-2.0, 74k downloads, 389 stars) on the `ort` crate (2.0.0-rc.13). Covers TDT/CTC (offline), EOU 120M (160 ms chunks), Nemotron EN and 3.5 (`transcribe_chunk` with 560 ms chunks), Unified, Multitalker, Sortformer. Models come from community HF repos (int8 and int4 Nemotron exports exist). No hotwords. CPU speed claim is only "significantly faster on my Mac M3 compared to Whisper metal". `ort` needs an onnxruntime binary (its `download-binaries` default) or a system lib. ([README](https://raw.githubusercontent.com/altunenes/parakeet-rs/master/README.md), [docs.rs](https://docs.rs/parakeet-rs))
- `parakeet.cpp` (mudler, MIT, v0.5.0 2026-08-01, pushed daily): ggml port with GGUF (f16/q8_0/K-quants), a flat C API (`libparakeet.so`) with `parakeet_capi_stream_begin/feed/finalize`, and byte-identical output to NeMo. CPU benchmark on a 20-core x86 at 8 threads: tdt-0.6b-v2 RTFx 32 (f32) / 35 (q8_0), RSS 2.5 GB f32; eou-120m RTFx 71 / 76, RSS 621 MB; Nemotron 3.5 offline RTFx 29 (f32) on a Ryzen 9 9950X3D, streaming path RTFx 3.8. Streaming support is EOU 120M and Nemotron 3.5; the English-only Nemotron is not listed. No Rust crate, no hotwords. ([README](https://raw.githubusercontent.com/mudler/parakeet.cpp/master/README.md), [BENCHMARK.md](https://raw.githubusercontent.com/mudler/parakeet.cpp/master/benchmarks/BENCHMARK.md))
- `transcribe.cpp` (handy-computer, MIT, 1.85k stars, pushed 2026-08-26) with the `transcribe-cpp` Rust crate 0.2.2 (2026-08-24, 26k downloads). ggml runtime, GGUF, tinyBLAS CPU path, Vulkan/CUDA/Metal, `dynamic-backends` so one binary can pick a CPU kernel set at runtime (Handy's logs show `libggml-cpu-haswell.so` loading). Streaming API `transcribe_stream_begin/feed/finalize` and `transcribe_stream_get_text()` returning committed and tentative text. Rust crate exposes `Model`, `Session`, `Stream::feed/finalize`. ([README](https://raw.githubusercontent.com/handy-computer/transcribe.cpp/main/README.md), [bindings.md](https://raw.githubusercontent.com/handy-computer/transcribe.cpp/main/docs/bindings.md), [docs.rs](https://docs.rs/transcribe-cpp))
  - Nemotron EN 0.6B in transcribe.cpp: cache-aware streaming with all four lookahead settings (`--stream-att-right 0/1/6/13`), Q8_0 696 MB, Q4_K_M 453 MB, WER 2.31% LibriSpeech clean streaming (matches NeMo). CPU on an AMD Ryzen 7 4750U Pro (8-core laptop): 11 s clip in 1.39 s Q8_0 (8x realtime), 35 s clip in 5.2 s (7x). Apple M4 Max CPU: 33x. ([doc](https://raw.githubusercontent.com/handy-computer/transcribe.cpp/main/docs/models/nemotron-speech-streaming-en-0.6b.md))
  - Moonshine streaming in transcribe.cpp: tiny 48 MB Q8_0 (4.52% clean), small 189 MB (2.54%), medium 282 MB (2.16%); ~240 ms encoder right-context, 80 ms feed cadence. No keyterm biasing in this port. ([doc](https://raw.githubusercontent.com/handy-computer/transcribe.cpp/main/docs/models/moonshine-streaming.md))
  - Custom vocabulary: none in the engine. Handy does post-hoc word correction (see above).
  - Build: cmake + C++ toolchain, optional `libopenblas-dev` which "accelerates the host-side decoder ~10-15x". The Rust crate builds it via a `-sys` crate reading a link manifest.

Verdict: Nemotron EN 0.6B is the model. Either sherpa-onnx (prebuilt, hotwords coming) or transcribe.cpp (Handy-proven on CPU, published Linux x86 numbers, no biasing) gets it into a Rust binary. parakeet-rs is a third option with less proof and an `ort` dependency.

### 5. Moonshine v2 (Useful Sensors / Moonshine AI)

- Code MIT; all streaming models MIT (only legacy non-English non-streaming models are non-commercial). v0.1.5 released 2026-08-24, pushed daily, 11k stars. ([license.md](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/docs/license.md), GitHub API)
- Models (paper, Feb 2026): tiny 33.6M, small 123.4M, medium 244.9M. Open ASR average WER 12.00 / 7.84 / 6.65. LibriSpeech clean 4.49 / 2.49 / 2.08. Ergodic sliding-window encoder (no positional embeddings), 80 ms lookahead per lookahead layer, provisional states decodable before the 320 ms finalization bound, autoregressive decoder. ([paper](https://arxiv.org/pdf/2602.12241), [available-models.md](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/docs/models/available-models.md))
- Latency, measured as time from end of speech to final transcript, Apple M3 CPU via their C++/onnxruntime library: v2 tiny 50 ms, small 148 ms, medium 258 ms, versus Whisper tiny 289 ms and large-v3 11,286 ms (faster-whisper). Compute load 8% / 18% / 29% of audio duration. No x86 numbers published; the docs admit the Linux x86 and Pi 5 columns are stale. ([paper Table 2](https://arxiv.org/pdf/2602.12241), [benchmarks.md](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/docs/using/benchmarks.md))
- Rust integration: no crate. Options are (a) FFI to the C API. The Linux x86_64 release tarball (14 MB) contains `include/moonshine-c-api.h`, `include/moonshine-cpp.h`, `lib/libmoonshine.so`, `lib/libonnxruntime.so.1`; bindgen over the header is straightforward and the API is documented as the "portable ABI" with a header-version handshake. (b) transcribe.cpp's GGUF port through the `transcribe-cpp` crate (no keyterms there). (c) `transcribe-rs` (Handy's ONNX crate) has a `StreamingModel` for Moonshine, but Handy has an open bug where Moonshine streaming truncates final text ([#1835](https://github.com/cjpais/Handy/issues/1835)). Two GitHub issues asking for a Rust port were closed without one. ([release assets](https://github.com/moonshine-ai/moonshine/releases/latest), [adding-the-library.md](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/docs/using/adding-the-library.md), [c-api.h](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/core/moonshine-c-api.h))
- Streaming C API: `moonshine_create_stream`, `moonshine_transcribe_add_audio_to_stream`, `moonshine_transcribe_stream` returning lines with `is_complete`, `is_updated`, `is_new`, `has_text_changed` flags and `lastTranscriptionLatencyMs`. Silero VAD is built in. ([c-api docs](https://moonshine-voice.readthedocs.io/en/latest/api/c-api/))
- Custom vocabulary: real contextual biasing, streaming models only. `keyterms` load option and `moonshine_transcriber_set_keyterms()` (comma-separated, phrases allowed, swappable mid-stream), plus `set_context()` which pulls rare words out of a passage of text (e.g. the document on screen). Mechanism: terms are tokenized into a prefix tree and a logit bonus of `boost * (1 + ln(depth))` is added to continuing subwords; default `keyterm_boost` 2.0 "removes about a quarter of the errors on the words you listed for at most a quarter of a point on everything else"; up to 40% error reduction claimed. Cost: 100 terms ~1 ms per phrase on tiny, 10,000 terms +3-4 ms. Limit: only helps words the tokenizer can already spell. ([domain-customization.md](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/docs/models/domain-customization.md))

Verdict: the only candidate that ships the biasing feature this project asked for, with low latency numbers and small models. The costs are an FFI layer of your own, a bundled onnxruntime .so (~13 MB), and English accuracy a step behind Nemotron on clean speech.

### 6. WhisperLive (Collabora) and SimulStreaming (UFAL)

Both are Python. Neither fits a single Rust binary; I'm assessing them so the comparison is fair.

- WhisperLive: MIT, v0.9.0 2026-06-02, pushed 2026-08-04. WebSocket client/server around faster-whisper (CTranslate2), TensorRT, or OpenVINO. Streaming is a growing audio buffer re-transcribed each pass; a segment is committed when its text repeats `same_output_threshold` times (default 10) or the buffer is clipped. Supports `initial_prompt` and `hotwords` (faster-whisper's `hotwords` is text prepended to the prompt when there is no previous context, so it's still a prompt hint). Server default `OMP_NUM_THREADS=1`. ([README](https://github.com/collabora/WhisperLive), [base.py](https://raw.githubusercontent.com/collabora/WhisperLive/main/whisper_live/backend/base.py), [faster-whisper transcribe.py](https://raw.githubusercontent.com/SYSTRAN/faster-whisper/master/faster_whisper/transcribe.py))
- SimulStreaming: MIT, PyTorch Whisper only, AlignAtt policy (uses cross-attention to decide when to stop emitting) plus LocalAgreement. README: "The code works also on CPU but would be too slow for real-time" and asks for a 10 GB GPU for large-v3. Has `--init_prompt` and `--static_init_prompt` for terminology. Pushed 2026-07-12, 665 stars. ([README](https://raw.githubusercontent.com/ufal/SimulStreaming/main/README.md))

Verdict: WhisperLive is an ok Python daemon design, but its "streaming" is the same window re-decode as whisper.cpp's stream example. SimulStreaming's AlignAtt idea is clever and the right way to stream Whisper, but it's GPU-bound and Python. Neither beats a natively streaming transducer on CPU.

### 7. Others

- faster-whisper / CTranslate2: MIT, v1.2.1 2025-10-31, last push 2025-11-19 (quiet). Offline API; CPU int8 small model does 13 min of audio in 1m42s single-batch on their benchmark box (~7.6x realtime). Rust binding exists: `ct2rs` 0.10.0 (2026-08-05, 50k downloads) with a `whisper` feature, builds CTranslate2 with cmake. Custom vocab via `initial_prompt` / `hotwords` prompt text. Still not streaming. ([faster-whisper](https://github.com/SYSTRAN/faster-whisper), [ct2rs README](https://raw.githubusercontent.com/jkawamoto/ctranslate2-rs/main/README.md))
- Vosk: Apache-2.0, Kaldi online decoding, true streaming with `partial_result`. English models: small 40 MB (LibriSpeech clean 9.85%), 0.22 1.8 GB (5.69%), 0.22-lgraph 128 MB (7.82%) with dynamic vocabulary; grammar lists restrict, not bias. No punctuation without a separate model. Last release v0.3.50 (2024-04), `vosk` crate 0.3.1 (2024-10) needs a manually downloaded `libvosk`. ([models](https://alphacephei.com/vosk/models), [repo](https://github.com/alphacep/vosk-api))
- Voxtral Mini 4B Realtime (Mistral, Apache-2.0, Feb 2026): natively streaming audio-LLM, 480 ms recommended delay, TEDLIUM 3.17%. 3.4B LM + 970M encoder, ~8.4 GB bf16 weights. antirez's `voxtral.c` on an M3 Max: encoder ~8 s and 335 ms per decoder step on the CPU/BLAS path, "usable but slow"; realtime only on Metal. transcribe.cpp also ports it. Too heavy for this CPU. ([card](https://huggingface.co/mistralai/Voxtral-Mini-4B-Realtime-2602), [voxtral.c](https://github.com/antirez/voxtral.c))
- onnx-asr (istupakov): the Python project behind the community Parakeet ONNX exports parakeet-rs uses. Python, so only relevant as a model source. ([repo](https://github.com/istupakov/onnx-asr))

## Recommendation

1. Build on Nemotron Speech Streaming EN 0.6B. It is the only English model in the set that is natively streaming, punctuated, within a point of offline Parakeet accuracy, and proven on CPU by Handy's users and transcribe.cpp's published Ryzen 4750U numbers (7 to 8x realtime at Q8_0, so a 16-thread Alder Lake has headroom for the 160 ms or 560 ms lookahead). Start with sherpa-onnx's Rust crate: the build is a download, endpointing is built in, and the hotwords PR gives a real biasing path once merged. Keep transcribe.cpp as the alternate runtime for the same model; its `committed/tentative` text API maps directly onto "text streams out while speaking", and it's what Handy already runs on Linux. Do Handy-style post-hoc custom-word correction regardless, since it's cheap and independent of the engine.
2. Add Moonshine v2 streaming (medium, or small for lower latency) as a second engine, through its C API. It has the biasing feature today, models are MIT, and its 148 to 258 ms end-of-phrase latency is the snappiest number anyone has published. Accept the FFI work and the bundled onnxruntime .so. If the sherpa-onnx hotwords PR stalls, this becomes the primary.
3. whisper.cpp via whisper-rs only as a compatibility option for users who want Whisper's multilingual coverage. Don't build the streaming UX around it.

Skip Kyutai and Voxtral for CPU. Skip the Python servers.

## What I could not verify

- No published benchmark of any candidate on Alder Lake specifically. The closest CPU data points are transcribe.cpp's Ryzen 7 4750U (Zen 2, 8 cores, AVX2, no VNNI) and parakeet.cpp's 20-core x86 at 8 threads. AVX-VNNI on Alder Lake should help int8/Q8_0 paths in both onnxruntime and ggml, but I found no measurement.
- Kyutai STT CPU speed: nothing in the README, model cards, or issues. My estimate that 1B params per 80 ms step is bandwidth-marginal on DDR4/DDR5 is arithmetic, not a measurement.
- Moonshine x86 latency: the paper's numbers are Apple M3; the docs say the Linux x86 column is stale and I could not find it. The `set_keyterms` accuracy numbers come from Moonshine's own LibriSpeech-derived test, not an independent one.
- sherpa-onnx's RTF 0.16 for Nemotron: the hardware behind that number is not stated on the page.
- Whether sherpa-onnx PR #3895 will merge, and how much beam search costs on this CPU at the 160 ms chunk.
- The exact whisper.cpp version whisper-rs 0.16 bundles, and the whisper.cpp version inside whisper-cpp-plus.
- Open ASR Leaderboard live values: the Space page did not render for fetching, so leaderboard averages come from the model cards and the Moonshine paper's plot.
- HF model cards for `moonshine-ai/moonshine-streaming-*` returned 401 (gated), so model sizes and WER come from the paper and the repo docs.
